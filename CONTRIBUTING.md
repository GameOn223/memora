# Contributing to Memora

Thanks for wanting to help. Memora is a local-first visual memory for Android, and it gets better every time someone fixes a rough edge or tells us where the docs lost them.

This guide covers setup and review, plus the few rules we hold firm on.

## Before you start

- Read [docs/architecture.md](docs/architecture.md). It's long, but it explains why the code is shaped the way it is, and most review comments point back to it.
- Look for issues labeled `good first issue` or `help wanted`. If you want to work on something bigger, open an issue first so we can agree on the approach before you spend a weekend on it.
- Be kind. We follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Ground rules

These come from the architecture doc and are enforced in review:

1. Core packages never contain vendor-specific logic. Providers live in `memora_providers`.
2. The original image is never modified. AI output is always regenerable.
3. Capture and import never wait on AI.
4. The chat model only reaches data through typed, read-only tools. No generated SQL.
5. Nothing leaves the device unless the user picked a provider that sends it, and local-only mode must never be bypassed.
6. Embeddings are always tagged with their model and version.
7. User data stays exportable.

If your change needs to bend one of these, say so in the PR description and explain why. We'd rather talk about it than find out in review.

## Setting up

You'll need:

- Flutter 3.47.4 (stable). `flutter --version` should report Dart 3.13.
- Android SDK with platform 36 and NDK 27.0.12077973, plus JDK 17. Android Studio's bundled JDK works.
- A phone or emulator running Android 8.0 or newer for anything that touches capture, gallery or background work.

Then:

```bash
git clone https://github.com/GameOn223/memora.git
cd memora
flutter pub get          # resolves the whole workspace
```

Run the checks CI runs:

```bash
dart format --output=none --set-exit-if-changed packages app/lib app/test app/pigeons
dart analyze --fatal-infos packages
(cd app && flutter analyze --fatal-infos)
(cd packages/memora_core && dart test)
(cd packages/memora_database && dart test)
(cd packages/memora_providers && dart test)
(cd app && flutter test)
```

Run the app:

```bash
cd app
flutter run
```

The Dart packages don't need a phone at all. If you're working on retrieval, chat, parsing or a provider, `dart test` on your laptop is the whole loop.

## Repository layout

```
app/                 Flutter app and the Android (Kotlin) layer
packages/
  memora_core/       domain model, ports, pipeline, retrieval, chat agent
  memora_database/   SQLite storage, FTS5, vectors, migrations
  memora_providers/  AI provider adapters
docs/                architecture and contributor docs
```

## Making a change

### Branches and commits

- Branch from `main` with a short prefix: `feat/`, `fix/`, `docs/`, `refactor/`, `test/`, `chore/`.
- Write commits in [Conventional Commits](https://www.conventionalcommits.org/) style with a scope when it helps: `fix(database): keep FTS row in sync on reprocess`.
- Keep pull requests focused. Two small PRs get reviewed faster than one large one.

### Tests

- New behavior needs a test. Bug fixes need a test that failed before the fix.
- Tests never call real AI APIs or the network. Provider tests use recorded fixtures with a mock HTTP client.
- Database changes need a migration test that upgrades from the previous schema version.

### Database changes

Never edit a migration that has shipped. Add a new numbered file in `packages/memora_database/lib/src/migrations/` and a test that migrates from the version before it.

### Bridge changes

The Dart and Kotlin bridge is generated by Pigeon from `app/pigeons/messages.dart`. After editing it:

```bash
cd app
dart run pigeon --input pigeons/messages.dart
dart format lib/src/platform
```

Commit the definition and both generated files together.

### Adding an AI provider

Follow [docs/providers.md](docs/providers.md). Most providers that speak the OpenAI API only need a preset. A provider with its own API needs a descriptor, a client, capability services and fixture-based tests.

### UI and copy

- Take colors, spacing and type from the theme. Don't hard-code values the tokens already carry.
- The accent is for outlines, marks and small highlights. Primary buttons are outlined.
- Copy should be short and plain. Say what happened and what the user can do next. Leave out jargon and exclamation marks, and use a colon or a period where you'd reach for an em dash.
- Every icon-only button needs a semantics label.

## Pull request checklist

- [ ] CI checks pass locally (format, analyze, tests).
- [ ] New behavior has tests.
- [ ] Docs are updated if you changed behavior, a schema, the bridge, or a provider.
- [ ] Screenshots or a short recording for visible UI changes.
- [ ] Tested on a device for changes to capture, gallery, background work or on-device inference.

## Using AI tools

You're welcome to use AI coding assistants when contributing. Plenty of good engineers do. What matters is the result and that you stand behind it.

- **You own the change.** Read and understand every line before you open the PR. If a reviewer asks why something works the way it does, you should be able to answer without going back to the tool.
- **Test it for real.** Run the tests, run the app, and try the edge cases yourself. Generated code that compiles but was never exercised will be sent back.
- **Keep it tidy.** Remove dead code, placeholder comments and unrelated reformatting before you push. Match the style of the files you touch.
- **Mind the licenses.** Only submit code you have the right to contribute under Apache 2.0.
- **Protect user data.** Never paste API keys, real screenshots from your gallery, or anyone's personal information into a third-party tool while working on Memora.

Maintainers may close a PR when the author can't explain the change, or when it looks like unreviewed output. Review time is limited, and we'd like to spend it on changes their authors understand. You don't need to disclose which tools you used, but mentioning it in the PR description is fine if it helps reviewers understand your process.

## Reporting bugs

Open an issue with the bug report template. Include your Android version, phone model, which providers you had selected, and steps to reproduce. Please strip personal content from screenshots and logs.

Security problems should not go in public issues. See [SECURITY.md](SECURITY.md).
